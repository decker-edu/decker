# Decker content authoring & validation

Decker compiles `*-deck.md`, `*-page.md`, and `*-quest.yaml` into HTML. When you
create or edit any of these, do not stop at writing Markdown — **build the file
and verify the output**, because several kinds of breakage don't fail the build.

## First: load the project guide

The authoritative, version-stamped syntax reference and build recipe live in
`.decker/agent-guide.md` in this project. Read it before authoring. If it is
missing, regenerate it with `decker agent-docs`; if that command is unavailable,
fall back to `CONTENT-FORMATS.md` at the project root. Always prefer the project
guide over your own memory — Decker's syntax evolves between versions (check
`decker version`).

This skill and the guide are the source of truth for **generic** Decker syntax
and validation. A project's `CLAUDE.md` should carry only **project-specific**
context (this repo's conventions, directory layout, naming, publishing target)
— it is not expected to teach Decker syntax, and this guide supersedes any
generic Decker how-to written there.

## The loop (do all three; never report done after step 1)

1. **Write** the content per `.decker/agent-guide.md`.
2. **Build the single target** and check the exit code. Source maps to `public/`
   mirroring its path (`unit/07-deck.md` → `public/unit/07-deck.html`):

   ```
   decker public/<path>.html 2>&1 | grep -E '\[WARNING\]|Error when running Shake'
   ```

   - **Exit 1** = hard error (missing include / image / resource); no HTML is
     produced. Fix the missing dependency.
   - **Exit 0 with `[WARNING]`** = build succeeded but content is wrong (e.g. an
     unresolved citation key rendered literally into the HTML). Fix it.
   - Ignore the `WARNING: You are running a development build` banner — match the
     **bracketed** `[WARNING]` form only.

3. **Inspect the generated HTML** for silent problems exit 0 won't catch:
   unresolved citation keys appearing literally, unresolved `§wen`/`§wde`
   Wikipedia links, stale output (force with `decker -B <target>`), or
   dropped/misparsed slides and questions. Grep the HTML for the strings you added.

## Quests / exams are different

`*-quest.yaml` files are **not** built per-file — they aggregate into the exam
browser. New quest files need a **forced** rebuild (an incremental build or
running server won't pick them up):

```
decker -B exam-builder
```

Verify the question landed in `public/exam-builder/questions.json` (grep its
`Title`/`TopicId`). Files sharing `LectureId`+`TopicId` are randomized exam
variants — keep them equal in difficulty and choice count.

## High-value gotchas

- `.live-code-` (trailing dash) is intentional Decker syntax — never "fix" it to
  `.live-code`.
- Slide separators are exactly 80 dashes; off-count runs silently merge slides.
- `[:include](path)` with a bad path is a hard (exit 1) failure — safe.
- Quest YAML is whitespace-sensitive; fenced code must stay indented under the
  `Question: |` block scalar.

See `.decker/agent-guide.md` for the authoritative, current details.
